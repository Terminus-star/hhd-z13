# Full audit — hhd-z13 + z13-hibernate-plus (2026-09-08)

Produced by a two-agent pass (Opus 5 critic verifying 114 raw findings from
13 independent read-only sweeps, then Sonnet 5 synthesizing) over both
codebases, cross-checked against the v0.2-era btrfs snapshot and the plan
docs. Two of the criticals below were re-verified by hand-tracing the actual
code before being trusted, and both were confirmed real:

- `tdp.py`'s `_hold_choice`/`_sync` collision — fixed same day, see git log
  ("Clear the transition hold when a preset edit forks to Custom").
- `common.sh`'s missing `--set` on `z13ctl-plus tdp` calls — mechanically
  confirmed real, but the suggested fix (add `--set`) does NOT actually work:
  the PPT sysfs nodes are `root:users rw-r--r--`, so even with `--set` the
  write would fail on permission, not succeed. This path is dead-by-design
  since hhd took over TDP ownership (`v040-tdp.sh` deliberately revoked the
  group-write grant). The correct fix is deletion, not repair — matches the
  earlier "Phase 0: drop today" finding from the dependency audit.

Everything below this line is the synthesis agent's report, unedited except
for that one correction folded into the relevant bug entry.

---

## 1. Verdict

Not sound as shipped, and the unsoundness is measured, not inferred: at least a dozen of these 48 findings are backed by direct evidence taken from this machine right now, not just static reading — including two of the four criticals. `tdp.py`'s post-resume hold is caught live re-locking TDP to 9 W (`state.yml`: `dc_preset=z13_p1`, `custom.tdp=9`, reapplied at every hhd start), and the GPU-compute-affinity timer has never fired across five boots (`LastTriggerUSec` empty, `NextElapseUSecMonotonic=infinity`). Other live evidence in the set: `scaling_min_freq` pinned at 2000000 on battery right now, the hibernate LED ramp marker frozen at index 11, a `.z13-orig` patch backup dated two months stale, and a `powerdevilrc` that only has correct settings because someone set them by hand in July.

One scope caveat outranks every individual finding: the running `hhd@termis.service` executes `hhd_z13` from the **main** checkout via an absolute editable-install mapping, not this `v0.2.0-stability` worktree. A fix landed here does nothing on the machine until it's merged, and hand-verifying with `python3 -m hhd_z13.aura` from inside a checkout silently tests a *third* copy again, because cwd shadows the package finder before the install mapping applies. This has already produced "I merged but nothing changed" three times (finding at `common.sh:23`, cross-repo contract).

Below that caveat, both repos are individually coherent in design — the edge-triggered TDP policy and the presets fork-to-Custom logic are deliberate and correct in isolation, and the sleep-hook ramp/escalation ladder is a genuinely well-thought-out piece of engineering. The damage is concentrated in the *seams*: TDP ownership across a resume, LED ownership since the z13ctl-plus daemon's retirement, session discovery, and the acceptance gate itself. The test suite currently can't see most of it — two of nine suites report `ALL PASS` while exercising nothing that would catch a regression, and the acceptance script exits 0 with hhd stopped.

## 2. Bugs

Ranked by severity as tagged in the verified findings. Two high-severity and one medium-severity efficiency finding are cross-referenced to the Energy table rather than repeated in full here.

#### Critical

- **`hhd_z13/tdp.py:548`** — `_hold_choice()` re-asserts the preset mode during its 15/60 s post-transition hold, colliding with `_sync`'s deliberate fork-to-Custom when the user edits the TDP slider.
  *Why:* recreates the reported "hard locked to 9 W" symptom via a different mechanism than the one already fixed for it — live now, not hypothetical.
  *Fix:* clear `self._hold` in the fork-to-Custom branch; cancel the hold on user action, don't out-guess the cause.

- **`z13-hibernate-plus/src/common.sh:232`** — `set_tdp()` calls `z13ctl-plus tdp --pl1 --pl2 --pl3` without `--set`, so the binary prints usage and exits 0 instead of writing anything.
  *Why:* every PPT write in the hibernate stack is a no-op that logs success; three live call sites believe they set limits they didn't.
  *Fix — CORRECTED:* adding `--set` does NOT fix this. `ppt_pl1_spl` is `root:users rw-r--r--` — the daemon runs as the user session and cannot write it either way; the group-write grant was deliberately revoked when hhd took over TDP ownership (`v040-tdp.sh`). This path is dead-by-design, not broken-by-accident. Delete `set_tdp()` and its four call sites (also line 752, and `safe_hibernate`'s callers), matching the earlier "Phase 0: drop today" recommendation.

- **`z13-hibernate-plus/src/common.sh:752`** — `safe_hibernate`'s last-resort thermal floor has the identical missing `--set`.
  *Why:* when hibernate/suspend-then-hibernate/suspend all fail — exactly the scenario this exists for — the SoC is left at whatever PL1 it had, in a closed bag, while the log asserts it was floored.
  *Fix:* same one-token fix; shares the root cause with the entry above.

- **`z13-hibernate-plus/src/s2idle-resume-fixup.sh:395`** — schedules `systemd-run ... safe_hibernate "..."`, passing a bash function to `systemd-run` as if it were an executable.
  *Why:* the unit fails at exec, `|| true` swallows it, and the following `exit 0` skips the long-sleep gate that would have scheduled hibernate correctly — the machine keeps s2idle-draining to flat.
  *Fix:* call an absolute-path script, as line 421 in the same file already does.

#### High

- **`hhd_z13/plugin.py:645`** — `_reexpand_ceiling()` runs on every tick whenever boost is on and widens `scaling_max_freq` back to max whenever `cur < hi` — exactly what a deliberately-lower manual ceiling looks like.
  *Why:* directly contradicts its own docstring ("never narrows... left alone"); a user-set 3000 MHz cap is silently widened to 5187 MHz within one tick, slider included.
  *Fix:* gate the widen on `freq_mode != "manual"`, as the docstring already claims it does.

- **`z13-hibernate-plus/src/post-resume-hook.sh:29`** — `apply_power_profile()`'s `set_profile` half writes `platform_profile` as root at T+15 after every hibernate resume, and the firmware resets PPT to that profile's defaults on the write.
  *Why:* `tdp.py`'s resume hold only watches its own mode variable, never `platform_profile`, so it can't see or correct this — the QAM can read 9 W while the firmware sits at ~60 W+ on battery, silently.
  *Fix:* stop this hook from writing `platform_profile` now that hhd/adjustor own PPT.

- **`z13-hibernate-plus/src/common.sh:1083`** — `restore_screen`'s `loginctl` column check is transposed against the live `SESSION UID USER SEAT` order, so both tests are always false and it falls back to `${SUDO_USER:-gunther}` — a user that doesn't exist.
  *Why:* the entire user-session wake block never runs after hibernate; on this machine the keyboard is the lid, so a lid-open produces no rescue event either, and the user is documented as hard-resetting because of exactly this.
  *Fix:* copy the already-correct field order from `user_is_present()` (`common.sh:852`) / `tdp_notify()` (`common.sh:905`) — see "What I would do next," item 3, for the other four sites sharing this defect.

- **`z13-hibernate-plus/src/post-resume-hook.sh:82`** — lighting restore is gated on `command -v z13ctl-plus` (the binary), not on the daemon actually running, and the daemon's units are symlinked to `/dev/null`.
  *Why:* nothing restores the user's configured RGB after hibernate; the last write standing is a hardcoded bright-green "transient" signal, stuck.
  *Fix:* check for the running daemon (there isn't one), and have this hook do the restore itself. See also section 4, Regressions.

- **`hhd_z13/aura.py:317`** — `apply()` unconditionally calls `set_power(True)`, enabling all four Aura power domains — shutdown included — on every LED write, with no parameter to skip it.
  *Why:* `hibernate-hook.sh` documents that the "dark means off, safe to close" contract *requires* the shutdown domain off, and the ramp's own last act turns it on in the same call — the panel stays lit after power-off.
  *Fix:* drive `set_power` from hhd's own existing per-domain settings instead of hardcoding all-on.

- **`/etc/systemd/system/z13-gpu-compute-affinity.timer.d/99-z13-interval.conf:10`** — the drop-in resets `OnUnitActiveSec=`, not realizing an empty `On*Sec=` clears the *whole* timer-value list, deleting the unit's own `OnBootSec=15s` with it.
  *Why:* with no `OnBootSec` the service never gets a first activation, so `OnUnitActiveSec` has nothing to chain from — confirmed dead across 5 boots.
  *Fix:* re-add `OnBootSec=15s` in the drop-in, after the reset line.

- **`hhd_z13/display.py:767`** — the Adaptive Sync code path returns before reaching the VRR block whenever `rate_mode != "manual"`, and Auto is the shipped default.
  *Why:* on a default install the dropdown never adopts, applies, or reconciles anything — it's decorative.
  *Fix:* let the adaptive-sync block run independently of the refresh-rate mode branch.

- **`hhd_z13/display.py:423`** — `_resolve_rate()` returns `None` on any backend but `kscreen`, so the refresh slider has no write path under gamescope, while the Manual reconcile still pulls gamescope's own rate back into the setting.
  *Why:* not just inert but actively reverted, and VT-switching into gamescope silently disables panel overdrive too, via the same reset.
  *Fix:* wire up `gamescope.set_refresh()` (already exists, never called), or suppress the reconcile-overwrite on that backend.

- **`hhd-patches/hhd-qam-toggle-patch.py:751`** — the stock-ppt QAM entries read only `Z1_DATA`'s AC wattage, never `performance_dc`.
  *Why:* Turbo on battery writes 65/81/93 W against adjustor's own 54 W DC limit for this device — the same envelope already tied to a 2026-06-10 EC-brownout hard reset.
  *Fix:* branch on power source and read the `_dc` key on battery, matching adjustor's own driver.

- **`hhd_z13/display.py:659`** — session re-discovery runs unthrottled every 2 s tick (2× `loginctl` + a full `/proc` walk). *(Efficiency-tagged; full cost detail in the Energy table.)*
  *Fix:* cache the session/compositor identity, re-discover only on a login/logout or compositor-restart signal.

- **`z13-hibernate-plus/src/hibernate-hook.sh:67`** — panic sysctls and the C-state hold are armed well before the `/run/z13-was-hibernated` marker exists, across a window containing a `modprobe -r` and a per-VM savestate loop.
  *Why:* a hook killed in that window (already happened once, ~90 s in) leaves panic sysctls armed with no marker to disarm them on the next boot — a normal 60 s D-state then panics and reboots the machine.
  *Fix:* create the marker before arming the risky window, not after it.

#### Medium

- **`s2idle-resume-fixup.sh:203`** — blanks the LED after `hibernate-hook.sh` has already written the terminal violet, while the S4 image write is still in progress.
  *Why:* dark is supposed to mean "safe to move" — here it means "still writing."
  *Fix:* skip the brightness-off step on the suspend-then-hibernate hibernate leg.

- **`common.sh:135`** — `/run/z13-hib-ramp` is only reset by `gate-hook.sh`, which suspend-then-hibernate never runs (currently frozen at 11, live).
  *Why:* zero LED progress feedback on the second sleep of a boot; even with the gate, integer interpolation repeats an index exactly when the gate ran longest.
  *Fix:* reset the ramp marker on every resume path, not only via the gate.

- **`s2idle-resume-fixup.sh:248`** — restores brightness only, on the premise "suspend never changed the effect" — its own pre-hook set a cycling effect three lines earlier.
  *Why:* with the lighting daemon gone, nothing repaints the static colour afterward — every s2idle resume leaves the keyboard cycling. See section 4.
  *Fix:* restore the effect, not just the brightness.

- **`common.sh:924`** — `snapshot_backlight` truncates its state file before checking whether the reading is non-zero.
  *Why:* the expected "lid dimmed it" case destroys a previously-good snapshot; suspend-then-hibernate hits this twice, guaranteeing the empty case and the documented 15%→40% rescue regression.
  *Fix:* don't truncate until a non-zero value is in hand.

- **`hhd_z13/plugin.py:529`** — commits `self.old_pstate` before `_apply_pstate()`'s verified-by-readback result is checked; discards that result entirely.
  *Why:* a refused mode transition permanently forces `schema_stale=True`, silently disabling the EPP/governor control underneath it — no log line, until hhd restarts.
  *Fix:* only commit `old_pstate` after the write is confirmed.

- **`hhd_z13/plugin.py:726`** — reconcile rounds 5187500 kHz to 5188 MHz (banker's rounding), the settings clamp writes it back to the declared max of 5187, next tick reads that as a user edit.
  *Why:* latent today (`freq_mode: default`); selecting Manual with boost on writes `scaling_max_freq` on all 32 policies every 2 s indefinitely. See Energy table.
  *Fix:* compare against the clamped value, or declare the max as 5188.

- **`hhd_z13/plugin.py:297`** — `_ensure_boost_for()` is a module function with no plugin reference, so it can never update `self.old_boost` after turning boost on.
  *Why:* on battery with Boost=Auto, raising the manual frequency ceiling turns boost on to make the write possible and it never turns back off, while the QAM still shows Auto.
  *Fix:* route the write through the plugin instance so `old_boost` reflects it.

- **`hhd_z13/plugin.py:357`** — `scaling_min_freq` pinned at 2000 MHz right now, live, on battery — 3.2× the hardware's 625 MHz floor. *(Full detail in the Energy table's persistent-drain addendum and in "Still to implement.")*
  *Fix:* adopt and release any live floor at plugin startup, not only on the two transition edges that currently never fire.

- **`hhd_z13/settings.yml:65`** — the EPP hint promises pinning `scaling_governor=powersave` "in the background"; `_apply_pref` never writes that.
  *Why:* under the `performance` governor this plugin can itself set, EPP becomes unwritable exactly as the hint warns — the slider changes, the hardware doesn't, nothing says so.
  *Fix:* implement the pin or delete the claim — this is a decision, not a wording fix.

- **`hhd_z13/tdp.py:627`** — preset ids are list positions; `_remove()` pops with no id remapping and leaves `self._hold` armed.
  *Why:* deleting preset 2 silently re-points `ac_preset`/`dc_preset` at whatever used to be next; if inside a hold window, the next tick re-asserts the id that no longer exists.
  *Fix:* store presets by a stable id; clear `self._hold` in `_remove()` (same mechanism as Critical #1's fix).

- **`hhd_z13/tdp.py:369`** — `settings()` does unguarded `int(p.get("tdp", 45))`, unlike the identical read in `prepare()`/`update()`, which are wrapped specifically because an uncaught exception removes the plugin permanently.
  *Why:* one malformed preset entry permanently kills the entire TDP-presets plugin, one warning line, no recovery short of a fix.
  *Fix:* wrap the same try/except already used elsewhere in the file.

- **`hhd-patches/hhd-qam-toggle-patch.py:1133`** — drops every disabled Aura device just before re-discovery, so a device that keeps enumerating but fails every write is re-added — and reported "updated" — on every tick.
  *Why:* each "updated" triggers a full hhd settings-tree rebuild and re-emit; a USB power-cycle that leaves the keyboard EIO-on-write becomes an indefinite once-per-2s rebuild storm. See Energy table.
  *Fix:* back off a repeatedly-failing device instead of re-adding it every tick.

- **`hhd-patches/hhd-qam-toggle-patch.py:203`** — `backup()` snapshots `.z13-orig` once and never refreshes it; confirmed stale (10 Jul vs. current 7 Sep).
  *Why:* a package upgrade leaves the stale backup in place, so a later `--revert` overwrites a newer install with July's sources.
  *Fix:* refresh the backup when it differs from a fresh unpatched copy, or version-stamp it and refuse to revert on mismatch.

- **`system/v040-acceptance.sh:185`** — a failed settings-tree API read counts as a skip, never a fail; exit code is fail-only.
  *Why:* with hhd stopped, the whole settings-tree/live-PPT section is silently skipped and the script still exits 0 — and its one live check is separately gated to `mode == "custom"`, which isn't this machine's actual mode either.
  *Fix:* a skipped mandatory section should fail the run.

- **`system/v040-acceptance.sh:75`** — warns a patch-table line is "superseded dead code," but it's the live, required `ppt-override` sentinel that routes presets through adjustor's custom-apply path.
  *Why:* the printed remediation — revert, then re-apply — combined with the stale-backup bug above, would restore a July-vintage adjustor over the current one.
  *Fix:* delete this check.

- **`hhd_z13/tdp.py:276`** — `_detect_sleep()` flags any wall-vs-monotonic delta over 5 s as a resume; this machine's RTC is confirmed local-time and the wall clock has already stepped ~10800 s across a boot.
  *Why:* the observed steps are backward (safe), but a forward NTP correction of the same size would misfire a system-wide wakeup event — re-applying lighting, dropping adjustor's cached battery limit, and re-locking TDP for 60 s — with a journal line asserting the machine slept.
  *Fix:* use a monotonic-only resume signal instead of a wall-clock delta. See "Still to implement," upstreaming.

- **`common.sh:23`** *(cross-repo contract)* — the running `hhd@termis.service` executes the **main** checkout, not this worktree; separately, `python3 -m hhd_z13.aura` run from inside a checkout resolves a third copy again.
  *Why:* a fix made here does nothing on the machine until merged, and hand-verification can report success while testing neither the machine's copy nor the fix's target — already happened three times. See Verdict.
  *Fix:* merge to main to go live; verify from a neutral cwd or by restarting the actual service.

- **`docs/tdp-presets.md:20`** — section 1 documents the abandoned preset design (load-on-select, save-back-on-edit) that the shipped code deliberately inverts. *(Full enumeration in "Still to implement.")*
  *Why:* the next person to touch presets, reading the primary design doc, would reimplement the exact immutability bug fork-to-Custom exists to avoid.
  *Fix:* delete or clearly mark section 1 historical.

- **`hhd_z13/firmware.py:167`** — commits `self.old[leaf]` before `_write()`'s success is checked; only the log line is gated on it.
  *Why:* a firmware-rejected write leaves the QAM toggle showing the new state permanently — no reconcile loop here to notice, unlike `display.py`/`plugin.py`.
  *Fix:* commit the cache only after `_write()` confirms.

- **`z13-hibernate-plus/Makefile:16`** — `PDUSER ?= gunther` (nonexistent), and all six `kwriteconfig6` PowerDevil lines are `-`-prefixed, so `make deploy` reports success while configuring nothing.
  *Why:* the correct PowerDevil config on this machine exists only because someone set it by hand in July; a fresh deploy leaves PowerDevil racing `z13-lid-watch` and auto-suspending on load-blind idle detection.
  *Fix:* default `PDUSER` to the logged-in user; drop the `-` prefixes so failure is visible.

- **`z13-hibernate-plus/src/resume-hook.sh:102`** — the transient `z13-post-resume-hook` unit has no `--collect`, so one non-zero exit (reachable under `set -euo pipefail`) leaves it `failed` forever, refusing every later run with that name.
  *Why:* one bad resume silently disables screen restore, lighting, GPU restart and marker cleanup for the rest of the boot — and the un-removed marker also disables lid-watch's re-suspend guard.
  *Fix:* add `--collect`, already used correctly for `z13-cstate-hold` two files over.

#### Low

- **`hhd_z13/aura.py:328`** — `apply()` discards every per-device write result, returns success as long as one device *opened*.

  *Fix:* propagate `_write()`'s per-device result into the return value.

- **`hhd_z13/tdp.py:317`** — resets to an empty preset list on any unrecognised shape, then persists that empty state over the original file with no backup.

## 4. Regressions vs the v0.2 snapshot

One coherent story, four sites: the retired z13ctl-plus daemon used to be the *final writer* for LED/lighting state and the thing that repainted it after a wake pass. Nothing was assigned that role when it was retired.

- **`post-resume-hook.sh:82`** (and `common.sh:1027`) explicitly defer lighting restore to a "daemon owns final state" branch. The daemon's units are symlinked to `/dev/null`. Nothing restores the user's configured colour — the last write standing is a hardcoded "transient" bright green.
- **`s2idle-resume-fixup.sh:248`** restores brightness only on resume, on the premise that "suspend never changed the effect." That was true only while the daemon repainted afterward. It doesn't anymore, so the pre-hook's cycling effect (`led_cycle`, three lines above the premise) persists after every lid-open.
- **`common.sh:242-253`** is a dead conditional whose own header describes a write that was removed — `if [ "$Z13_LED_BACKEND" = none ]; then :` doing nothing — and **`z13-state.sh:270`** still restarts the retired daemon's systemd units and documents it in comments as the hardware owner. Automation is actively maintaining a component that shouldn't exist.
- **`aura.py:317`**, narrowly: `--brightness off` in the new stdlib port also sends `set_power(True)` — by the finding's own words, "not equivalent to the daemon's brightness off it replaced." Same command, different, worse, behavior than what it replaced.

This is the most systemic regression in the audit — an entire subsystem lost its owner during the daemon's retirement, and the four sites above are what's left of the handoff that never happened. (`tdp-restore.sh` being un-retired, `common.sh:934`, looks similar on the surface but is the opposite pattern — old code coming *back* rather than a role going unfilled — and stays classified as a bug in section 2.)

**Upstreaming candidates**
- **adjustor's mode routing.** `hhd-qam-toggle-patch.py` patches `if mode == "custom" or (mode and mode not in ...)` into adjustor's asus driver so unrecognized/preset mode names route through the custom-apply path. Proposing this natively in adjustor — any downstream-defined mode falls through to custom-apply without a patch — would retire both the local patch and the `v040-acceptance.sh:75` misdiagnosis that currently tells the operator to revert it. Strongest candidate in the set: it removes a bug and a patch in one motion.
- **A reliable resume signal in hhd core.** hhd's own wakeup event is unreliable across hibernate, and there are now at least two independent local workarounds for that fact: `tdp.py`'s wall-vs-monotonic-clock heuristic (`tdp.py:276` — shown here to have a real forward-NTP-step false-positive exposure, since this machine's RTC is confirmed local-time) and adjustor's own new battery-driver `notify()` cache-drop patch. A `CLOCK_BOOTTIME`-based resume signal contributed to hhd core would retire both local heuristics and the false-positive risk at once, rather than each plugin re-deriving its own fragile version.
- Adjacent, not quite the same shape: hhd already ships a correct per-domain Aura power-command builder (`get_aura_power_cmd()`), and `hhd_z13/aura.py` reinvented a simplified always-on version instead of reusing it. Not an upstream contribution — the fix is for this repo to call what upstream already has.
